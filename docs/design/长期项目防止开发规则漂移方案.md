# 长期项目防止开发规则漂移方案

## 一句话结论

防止开发规则和约定漂移，不能主要依赖“提醒大家遵守文档”，而要把规则变成一套可执行、可审计、可演进的工程治理系统：

> **规则文档化，规则代码化，规则自动检查，合并前强制门禁，例外受控，定期审计。**

---

## 核心模型

```text
ADR / RFC / 规则文档
        ↓
Rulebook as Code
        ↓
本地检查：formatter / linter / pre-commit
        ↓
CI 检查：测试 / 架构规则 / 安全规则 / API 契约
        ↓
合并门禁：branch protection / required checks / CODEOWNERS
        ↓
Policy as Code：OPA / Conftest / Kyverno / Sentinel
        ↓
例外治理：waiver / owner / expiry / migration plan
        ↓
周期审计：drift audit / scorecard / dashboard
        ↓
平台化复用：Golden Path / shared templates / developer platform
```

---

## 规则分级

| 等级 | 含义 | 执行方式 |
|---|---|---|
| **MUST** | 不允许违反 | CI 阻断、合并门禁、policy check |
| **SHOULD** | 推荐遵守，可解释性偏离 | PR 提醒、review checklist |
| **MAY** | 建议或偏好 | 文档、示例、onboarding |

关键原则：

> **MUST 级规则应尽量自动化检查；不能自动化的规则，必须有明确 owner 和 review 路径。**

## 四道防线

### 1. 本地开发防线

用于提前反馈，不作为最终权威。

- `.editorconfig`
- formatter：Prettier、Black、gofmt、rustfmt
- linter：ESLint、Ruff、Checkstyle、Clippy
- pre-commit hooks

### 2. PR 防线

PR 是最重要的防漂移关口。

必须检查：

- 格式化检查
- lint 检查
- 单元测试 / 集成测试
- 架构边界检查
- API schema / contract 检查
- dependency / license / security 检查
- CODEOWNERS 审查

### 3. 主干保护防线

对 `main` / `master` / release 分支设置保护：

- 禁止直接 push
- 禁止 force push
- 必须通过 PR 合并
- 必须通过 required checks
- 必须有 reviewer
- 关键目录必须有 CODEOWNER approval
- bypass 必须有审计记录

### 4. 周期审计防线

定期检查系统本身有没有漂移：

- 是否使用最新 CI 模板
- 是否开启 branch protection
- CODEOWNERS 是否覆盖关键目录
- waiver 是否过期
- lint suppression 是否持续增长
- deprecated API 是否仍在使用
- 依赖版本是否落后
- ADR 是否过期或失效

## 例外治理

规则漂移经常从“这次先破例”开始。因此例外必须被管理。

示例：

```yaml
waivers:
  - id: WAIVER-2026-001
    rule: ARCH-001
    path: "src/legacy/reporting/**"
    reason: "legacy reporting 模块短期无法完成分层改造"
    owner: "@reporting-team"
    approved_by: "@architecture-team"
    expires_at: "2026-08-31"
    migration_plan: "docs/migrations/reporting-layer-refactor.md"
```

CI 规则：

| 情况 | 行为 |
|---|---|
| 无 waiver，违反 MUST 规则 | 阻断 |
| 有未过期 waiver | 放行，但提示 |
| waiver 过期 | 阻断 |
| waiver 无 owner | 阻断 |
| waiver 无迁移计划 | 阻断 |

## 成熟系统方案

### 单仓库 / 小团队

优先落地：

1. `CONTRIBUTING.md`
2. ADR
3. formatter + linter
4. pre-commit
5. CI required checks
6. branch protection
7. CODEOWNERS
8. PR template
9. waiver 机制

### 多仓库 / 中型团队

增加：

1. 共享 CI workflow
2. 共享 linter / formatter 配置
3. 统一项目模板
4. 组织级 branch rules / rulesets
5. Policy as Code
6. dependency update bot
7. drift audit dashboard

### 大型组织 / 平台工程

平台化：

1. Internal Developer Platform
2. Backstage / Golden Path
3. 中央 policy service
4. 跨仓库 scorecard
5. 自动模板升级
6. 统一安全、合规、发布门禁
7. 轻量 architecture board / RFC 流程

## 90 天落地路线

### 第 1 阶段：规则盘点

产出：

- rules inventory
- MUST / SHOULD / MAY 分级
- enforcement map
- drift hotspots

### 第 2 阶段：建立最小门禁

优先完成：

- formatter check
- linter check
- test check
- branch protection
- required status checks
- CODEOWNERS
- PR template

### 第 3 阶段：自动化架构规则

重点检查：

- 分层架构是否被破坏
- 模块依赖方向是否正确
- 新 API 是否补充 schema
- 生产配置是否安全
- 是否引入禁止依赖

### 第 4 阶段：治理例外和技术债

建立：

- waiver registry
- expiry date
- owner
- migration plan
- scheduled audit

### 第 5 阶段：平台化复用

抽象为：

- shared CI template
- shared policy package
- shared coding standard package
- shared project template
- onboarding guide
- Golden Path

## 最终建议

防止长期项目开发规则漂移的最佳方案，不是增加更多人工提醒，而是建立：

> **Engineering Governance as Code**

它的核心是：

1. **规则有来源**：ADR / RFC / rulebook
2. **规则有分级**：MUST / SHOULD / MAY
3. **规则可执行**：formatter / linter / tests / policy
4. **规则能阻断**：CI + branch protection
5. **规则有负责人**：owner / CODEOWNERS
6. **例外有期限**：waiver + expiry + migration plan
7. **系统会自检**：drift audit + scorecard
8. **正确路径更容易**：Golden Path / platform templates

最终目标是：

> **让正确做法成为默认路径，让错误做法无法无声进入主干，让例外不会变成新常态。**

## 本仓库落地方案：规则文档 + ADR + Git 分支 + 主干保护

本仓库的防漂移方案采用“规则来源清晰、并行工作用 Git 隔离、主干由门禁保护”的模型。

### 规则来源

- AI 助手入口仍是 [CLAUDE.md](../../CLAUDE.md) <!-- pathref: repo/CLAUDE.md -->。
- 仓库级规则正文放在 [docs/rules/index.md](../rules/index.md) <!-- pathref: docs/rules/index.md -->。
- 重大规则和治理决策放在 [docs/adr](../adr) <!-- pathref: docs/adr -->。
- ADR 记录“为什么这样定”，规则文档记录“现在必须怎么做”。

### 多 AI Agent 并行协作

- 并行写入时，每个 AI agent 使用独立 Git 分支。
- 不允许多个 agent 在同一写入分支上并行修改 repo-tracked 文件。
- 所有主干改动必须通过 PR。
- 远端规则可用时，最终权威是 CI required checks、branch protection 和 CODEOWNER review。
- GitHub Free 私有仓库等远端规则不生效的场景下，主干保护下沉为代码化本地门禁：`.githooks/pre-push` 调用 `scripts.research.governance.branch_protection pre-push`，阻断直接推送 `main` / `master`。
- 不采用任务登记。Git 分支、commit、diff、PR 和 review 已经提供协作追踪，不再自建低配任务登记系统。

### 主干保护与门禁

需要补齐并保持：

- [CODEOWNERS](../../CODEOWNERS) <!-- pathref: repo/CODEOWNERS -->
- [.github/pull_request_template.md](../../.github/pull_request_template.md) <!-- pathref: repo/.github/pull_request_template.md -->
- [.githooks/pre-push](../../.githooks/pre-push) <!-- pathref: repo/.githooks/pre-push -->
- GitHub branch protection / rulesets
- required checks
- waiver 机制：[docs/exceptions/active-waivers.yaml](../exceptions/active-waivers.yaml) <!-- pathref: docs/exceptions/active-waivers.yaml -->
- scheduled drift audit

关键路径必须 owner review：

- `CLAUDE.md`
- `AGENTS.md`
- `docs/rules/**`
- `docs/adr/**`
- `.claude/skills/**`
- `.github/workflows/**`
- `.githooks/**`
- `scripts/research/governance/**`
- `scripts/research/registry/**`
- `path_aliases.json`
- `strategies/**`

### Governance Gate 扩展

[scripts.research.governance](../../scripts/research/governance) <!-- pathref: scripts/research/governance --> 需要检查：

- `docs/rules/index.md` 是否存在。
- `docs/adr/` 是否存在且 ADR 编号连续。
- `CLAUDE.md` 是否引用仓库规则文档和 ADR。
- `AGENTS.md` 是否仍指向 `CLAUDE.md`，没有另立规则。
- CODEOWNERS 是否覆盖关键目录。
- `.githooks/pre-push` 是否仍调用代码化主干保护门禁。
- PR 模板是否包含规则同步、检查结果、waiver、证据链接。
- waiver 是否有 owner、批准人、过期时间和迁移计划。
- 规则入口、Skill、README、workflow、registry、catalog 和 pathref 是否同步。

### 规则变更流程

任何 MUST 级规则变更必须：

- 修改对应 `docs/rules/*.md`。
- 如影响协作模型、目录结构、治理门禁或策略开发流程，新增或更新 ADR。
- 同步 `CLAUDE.md` 和相关 Skill。
- 通过 governance gate 和 pathref 校验。
- 经过 CODEOWNER review。
