# 飞书交易通知工具设计

## 目标

为聚宽模拟交易提供一个飞书通知工具，行为参考 [RelayTools.py](../../../../scripts/archive/RelayTools.py) <!-- pathref: repo/scripts/archive/RelayTools.py -->。策略只需要导入工具文件，不关心消息发送、订单合并、签名和失败处理。

## 已确认决策

- 通知通道使用飞书自定义群机器人 webhook。
- 工具采用 `RelayTools.py` 风格：导入即自动包装聚宽下单函数。
- 不使用聚宽内置微信通知，因为免费模拟交易位通常延迟到次日凌晨运行，无法满足该通知需求。
- 不依赖 `after_trading_end`，避免策略日终逻辑和通知逻辑耦合。
- 通过静默窗口合并订单：连续一段时间没有新订单后，把缓存订单合并成一条飞书消息。
- 使用 `atexit` 作为退出兜底：如果进程退出时还有未发送订单，尝试补发。
- 发送前先写本地 outbox，再尝试飞书发送；发送失败的消息允许后续补发。
- 补偿目标是降低漏通知风险，允许极少量重复消息，不承诺精确一次送达。
- 仓库不保存真实 webhook 或飞书签名密钥。

## 飞书官方约束

飞书自定义机器人适合把外部事件通过 webhook 单向推送到群。官方说明支持文本、富文本、交互式卡片等消息格式；本工具先采用文本消息，降低聚宽环境兼容风险。官方说明见 <https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN> 和 <https://www.feishu.cn/content/7271149634339422210>。

安全设置有三类：

- 自定义关键词：只接收包含关键词的消息。
- IP 白名单：只接收白名单 IP 发出的消息。
- 安全密钥：请求体携带 `timestamp` 和 `sign`。

本工具默认推荐安全密钥。IP 白名单不作为默认方案，因为聚宽云端出口 IP 不一定稳定。若用户启用关键词校验，工具必须保证标题或正文固定包含 `SECURITY_KEYWORD`，否则飞书会拦截消息。

签名实现约束：

- `timestamp` 使用秒级时间戳。
- `string_to_sign` 为 `"{timestamp}\n{secret}"`。
- 使用 HMAC-SHA256 后再 Base64 编码。
- 请求体顶层包含 `timestamp`、`sign`、`msg_type` 和 `content`。

频控约束：

- 飞书自定义机器人频控为单租户单机器人 `100 次/分钟，5 次/秒`。
- 触发限流时可能返回 HTTP `429`，响应头包含 `x-ogw-ratelimit-reset`。
- 官方建议出现限流时等待该响应头指定秒数后重试。
- 多个策略共用同一机器人且集中在凌晨运行时，可能出现同秒发送；工具应支持 `SEND_JITTER_SECONDS` 随机错峰。

## 范围

## 使用方式

每个聚宽策略只需要导入同一个工具文件。策略业务代码不调用通知函数，也不维护消息缓存。

推荐在聚宽研究环境或策略文件所在目录上传私有版 `FeishuRelayTools.py`。私有版包含真实 webhook 和 secret；仓库中的版本只保留占位配置。

为了让包装覆盖策略可见的下单函数，导入位置沿用 `RelayTools.py` 的约束：在策略运行前执行导入即可。若聚宽模块加载顺序存在差异，实施时需要用最小策略在聚宽云端验证包装数量和订单捕获日志。

## 组件设计

### 配置区

配置区包含：

- `feishu_enabled`：是否启用飞书通知。
- `WEBHOOK_URL`：飞书机器人 webhook，占位符版本不填真实值。
- `WEBHOOK_SECRET`：飞书签名密钥，占位符版本不填真实值。
- `SECURITY_KEYWORD`：可选关键词校验文本，启用后每条消息必须包含。
- `BUFFER_WAIT_TIME`：静默窗口秒数。
- `SEND_JITTER_SECONDS`：发送前随机错峰秒数，降低多策略同秒触发限流概率。
- `MAX_BUFFER_SIZE`：单条消息最多保留的订单数。
- `REQUEST_TIMEOUT_SECONDS`：飞书请求超时。
- `RETRY_DELAYS_SECONDS`：普通失败的退避重试间隔。
- `OUTBOX_PATH`：聚宽研究文件中的 outbox 路径。
- `OUTBOX_REPLAY_LIMIT`：每次启动最多补发的历史 pending 批次数。
- `TARGET_FUNCTIONS`：需要包装的聚宽下单函数名。

默认建议：

- `BUFFER_WAIT_TIME` 初始取 `60` 秒，适配日频或周频集中调仓。
- `SEND_JITTER_SECONDS` 初始取 `30` 秒，适配多个策略共用同一飞书机器人。
- `MAX_BUFFER_SIZE` 初始取 `30` 条，超过时保留最后订单并提示前略条数。
- `REQUEST_TIMEOUT_SECONDS` 初始取 `3` 秒，避免通知请求长时间占用策略进程。
- `RETRY_DELAYS_SECONDS` 初始取 `[30, 120, 300]`。
- `OUTBOX_PATH` 初始取 `feishu_relay_outbox/{strategy}.jsonl`。

### 策略名识别

工具按 `RelayTools.py` 的方式尝试从聚宽策略文件首行读取策略名。读取失败时回退为“未命名策略”。

消息标题必须包含策略名，方便多个策略复用同一个工具文件时区分来源。

### 下单函数包装

工具导入时扫描 `user_code` 和 `kuanke.user_space_api` 模块，包装以下函数：

- `order`
- `order_value`
- `order_target`
- `order_target_value`
- `order_target_percent`

包装函数只做三件事：

- 调用原始下单函数。
- 如果返回订单对象或订单列表，则提取订单摘要并加入缓冲区。
- 原样返回原始下单结果。

包装层不得改变下单参数、不得重试下单、不得吞掉原始下单异常。

### 订单摘要

每条订单摘要尽量包含：

- 时间。
- 买入或卖出。
- 证券名称。
- 证券代码。
- 委托数量。
- 委托价格。
- 策略名。

如果部分字段缺失，工具应降级输出可用字段，不因字段缺失影响策略运行。

### 静默窗口合并

订单进入缓冲区后，工具启动或重置一个 `threading.Timer`。

如果静默窗口内又有新订单，旧 timer 被取消并重新计时。只有当静默窗口内没有新订单时，工具才把缓存订单合并成一条飞书消息。

该机制用于避免一次集中调仓短时间连续触发飞书门禁。

### 退出兜底

工具注册 `atexit` flush。进程结束时如果缓冲区还有订单，尝试发送一次合并消息。

`atexit` 仅作为兜底，不作为唯一发送路径。聚宽运行环境若没有稳定触发退出钩子，主路径仍由静默窗口完成。

### Outbox 补偿

交易通知属于高价值消息，不能只依赖一次 HTTP 请求。工具采用 outbox 模式降低漏通知风险。

发送流程：

1. 静默窗口结束后，把当前缓冲订单组装成一个批次。
2. 为批次生成 `batch_id`，建议由策略名、交易日期、订单数和订单摘要 hash 组成。
3. 先用 `write_file(..., append=True)` 写入 outbox 的 `pending` 记录，记录消息原文、订单摘要、批次 ID 和创建时间。
4. 再调用飞书 webhook。
5. 飞书确认成功后，再向 outbox 追加同一 `batch_id` 的 `acked` 记录。

启动补偿：

- 工具导入时尝试读取 outbox。
- 找出只有 `pending`、没有 `acked` 的批次。
- 在 `OUTBOX_REPLAY_LIMIT` 范围内补发。
- 补发消息标题必须带 `[补发]` 和 `batch_id`，方便人工识别重复。

失败重试：

- HTTP 限流时读取 `x-ogw-ratelimit-reset`，按该秒数延后重试。
- 非限流错误使用 `RETRY_DELAYS_SECONDS` 做短退避重试。
- 重试通过 `threading.Timer` 调度，不阻塞下单函数。
- 重试耗尽后保留 outbox pending 状态，等待下次工具启动补发。

送达语义：

- 目标是降低漏通知风险。
- 允许极少量重复通知。
- 不保证精确一次送达。
- 任何补偿逻辑不得影响策略交易执行。

### 飞书发送

飞书发送使用 `requests.post`。

消息格式先采用文本消息，优先保证兼容性和稳定性。后续如果需要更清晰的展示，再考虑飞书卡片消息。

启用签名时，发送载荷包含时间戳和签名字段。签名算法遵循飞书自定义机器人文档的约定，使用 Python 标准库完成，不新增第三方依赖。飞书官方自定义机器人指南见 <https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN>。

响应处理必须同时检查：

- HTTP 状态码。
- JSON 响应中的 `code` 和 `msg`。
- 限流响应头 `x-ogw-ratelimit-reset`。

只有 HTTP 成功且响应 `code` 为 `0` 时，才把批次标记为 `acked`。

### 错误处理

通知错误不得影响策略交易。

处理规则：

- 飞书 HTTP 请求失败：记录日志，保留 outbox pending，不抛出。
- 飞书响应 `code != 0`：记录 `code/msg`，保留 outbox pending。
- 飞书限流：按 `x-ogw-ratelimit-reset` 延后重试，缺失该响应头时按普通退避重试。
- webhook 或 secret 缺失：记录配置错误，不发送。
- outbox 写入失败：记录错误，仍尝试发送；但日志必须标记“无持久化补偿”。
- outbox 读取失败：跳过启动补发，记录错误，不影响本轮交易通知。
- 订单字段读取失败：跳过该字段或记录简化订单。
- timer 或 flush 内部异常：捕获并记录。

日志不得打印完整 webhook 或 secret。

## 安全边界

真实 webhook 和 secret 只允许存在于聚宽私有上传版或本地未跟踪文件。

仓库内只允许出现：

- 占位符。
- 示例配置。
- 测试用假值。
- 防泄露说明。

实现阶段需要检查 `.gitignore` 是否覆盖私有上传产物。如果需要新增生成脚本，输出目录应放在 `.local/` 或其他未跟踪目录。

密钥泄露属于仓库 P0/P1 级风险，评审规则见 [review-guidelines.md](../../../../docs/rules/review-guidelines.md) <!-- pathref: docs/rules/review-guidelines.md -->。

## 测试设计

本地测试不调用真实飞书。

应覆盖：

- 包装函数原样返回订单对象。
- 单笔订单进入缓冲区。
- 多笔连续订单在静默窗口内合并为一条消息。
- 超过 `MAX_BUFFER_SIZE` 时前略提示正确。
- 飞书签名载荷包含时间戳和签名字段。
- 飞书安全关键词启用时，消息包含 `SECURITY_KEYWORD`。
- `SEND_JITTER_SECONDS` 启用时，发送调度被错峰。
- 请求失败不抛异常，且保留 pending。
- HTTP `429` 或频控错误按 `x-ogw-ratelimit-reset` 调度重试。
- 普通失败按 `RETRY_DELAYS_SECONDS` 调度重试。
- 成功发送后追加 `acked`，并且不会再次补发该批次。
- 启动时会补发未 ack 的 pending 批次。
- 订单字段缺失时降级输出。
- `flush` 后缓冲区清空，重复 flush 不重复发送。

测试使用 mock 替代 `requests.post`、`threading.Timer`、`read_file`、`write_file` 和订单对象。

## 主要风险

- 聚宽环境可能限制外网请求或请求飞书失败。处理方式：失败只记录日志，并保留最小人工冒烟要求。
- `threading.Timer` 在聚宽环境行为可能和本地不同。处理方式：静默窗口为主路径，`atexit` 为兜底，云端冒烟确认。
- 导入时模块加载顺序可能影响包装覆盖。处理方式：实现时记录包装数量，并在使用说明里要求确认日志。
- 飞书门禁仍可能被触发。处理方式：默认较长静默窗口，并只发送合并消息。
- 多策略共用同一机器人可能在同秒触发飞书 `5 次/秒` 限制。处理方式：默认开启发送错峰，并按飞书限流响应头重试。
- 网络超时后可能出现“飞书已收到但本地未确认”。处理方式：outbox 补发允许重复消息，补发标题带 `[补发]` 和 `batch_id`。
- outbox 文件可能变大。处理方式：实现阶段设置只读取最近记录或限制补发条数，必要时后续增加归档。
- 多策略共用同一工具文件时策略名可能读取失败。处理方式：允许手工配置策略名作为兜底。
