## 1. 测试目标

本测试方案用于重新梳理 `etf_factor_rotation` 策略的测试覆盖边界，确保本地可测试逻辑、聚宽云端运行逻辑、回测结果分析逻辑形成闭环。

核心目标：

- 覆盖完整的策略链路：参数初始化、取数、信号、权重、风控、交易执行、日志审计、回测归档。
- 明确本地 pytest 能验证什么，聚宽云端必须验证什么，避免用 mock 测试替代真实云端行为。
- 将性能测试作为专项覆盖，持续监控取数次数、单次调仓耗时、云端回测总耗时、日志/profile 开销。
- 为后续每次策略修改提供可复用测试用例，降低未来函数、取数结构变化、下单失败不可见等风险。
- 将测试证据沉淀到策略目录，保证他人可以复现测试过程和回测结论。

不在本方案内完成的事项：

- 不把本地测试等同于真实交易验证。
- 不基于一次回测收益率直接判断策略优劣。
- 不把参数优化、择时研究、资产池扩展混入本轮测试范围。

## 2. 测试分层

| 层级 | 名称 | 运行位置 | 主要目标 | 阻断级别 |
|---|---|---|---|---|
| L0 | 静态检查 | 本地 | 语法、路径引用、导入依赖、函数存在性 | 必须通过 |
| L1 | 单元测试 | 本地 | 纯函数、边界条件、参数初始化、权重约束 | 必须通过 |
| L2 | 本地集成测试 | 本地 mock 聚宽环境 | `weekly_check` 完整链路、取数参数、日志与下单调用 | 必须通过 |
| L3 | 本地性能测试 | 本地 mock/合成数据 | 单函数耗时、完整调仓耗时、API mock 调用次数、性能回归 | 发布前必须通过 |
| C0 | 云端冒烟测试 | 聚宽回测 | 上传、初始化、定时任务、真实 API 可用性 | 必须通过 |
| C1 | 云端场景测试 | 聚宽回测 | 真实行情、真实交易日历、真实下单撮合与日志 | 必须通过 |
| C2 | 云端回归测试 | 聚宽回测 | 长周期稳定性、关键指标、版本间差异 | 发布前必须通过 |
| C3 | 云端性能测试 | 聚宽回测 | 回测总耗时、单次调仓耗时、profile 与日志开销 | 发布前必须通过 |

本地测试负责“逻辑正确性”，云端测试负责“聚宽真实运行正确性”。两者缺一不可。

## 3. 当前风险驱动测试重点

| 风险 | 说明 | 主要测试层 |
|---|---|---|
| 未来数据 | 周一开盘调仓使用日线数据，必须确保不读取当日收盘价 | L2、C1 |
| 聚宽返回结构 | `get_price(pool, panel=False, skip_paused=True)` 的真实返回结构可能和 mock 不完全一致 | C0、C1 |
| 场内基金复权口径 | `use_real_price=True` 与 `fq='pre'` 对信号和成交可能有影响 | C1 |
| RSRS 失效 | 长窗口滚动计算可能因样本长度或方差异常退化为 1 | L1、C1 |
| 拥挤度惩罚失效 | 五类指标分位数可能因成交额缺失、窗口不足退化 | L1、C1 |
| 组合波动率缩放失效 | 高波动场景应能把总仓位按比例缩小 | L1、C1 |
| 下单不可审计 | 停牌、下单失败、阈值跳过、目标仓位需要可追踪 | L2、C1 |
| 交易约束误伤 | `MaxWeight`、`MinWeight`、`RebalanceThreshold` 应不重新归一化 | L1、L2 |
| API 调用过多 | 每次调仓若退化为逐 ETF 多字段取数，会放大云端 API 调用和耗时 | L3、C3 |
| 滚动计算变慢 | RSRS、拥挤度、组合波动率窗口较长，未来扩展资产池后可能明显变慢 | L3、C3 |
| 日志/profile 开销 | `enable_profile()` 和高频详细日志可能影响云端长周期回测速度 | C3 |
| 长周期性能退化 | 策略功能正确但回测耗时显著增加，影响迭代效率和云端稳定性 | C2、C3 |

## 5. 性能测试专项方案

性能测试的目标不是追求极限速度，而是防止策略在云端“逻辑正确但跑不动”。本策略的主要性能压力来自四处：聚宽 API 取数次数、RSRS 长窗口滚动、拥挤度多指标滚动、长周期回测下的日志和 `enable_profile()` 开销。

### 5.1 性能指标

| 指标 | 测量位置 | 关注点 | 阻断规则 |
|---|---|---|---|
| `pytest_total_seconds` | 本地 | 本地测试总耗时 | 较最近稳定基线增加超过 50% 需解释 |
| `weekly_check_seconds` | 本地/云端 | 单次调仓完整链路耗时 | 较基线增加超过 50% 需解释 |
| `get_price_call_count` | 本地 | 每次调仓 API 调用次数 | 默认资产池下应为 4 次 |
| `rsrs_seconds` | 本地 | `compute_rsrs_multipliers` 长窗口计算耗时 | 较基线增加超过 50% 需解释 |
| `crowd_seconds` | 本地 | `compute_crowd_penalties` 多指标滚动耗时 | 较基线增加超过 50% 需解释 |
| `cloud_backtest_seconds` | 聚宽云端 | 同区间完整回测总耗时 | 较上一稳定版本增加超过 30% 需解释 |
| `log_volume_per_rebalance` | 聚宽云端 | 单次调仓日志量 | 默认不应输出逐日、逐窗口明细 |
| `profile_overhead` | 聚宽云端 | `enable_profile()` 对长回测影响 | 正式长周期回测需评估是否关闭 |

性能阈值采用“基线 + 变化率”方式，而不是固定秒数。原因是本地机器、聚宽云端负载、回测区间都会影响绝对耗时。首次执行性能测试时，应把结果写入回测报告或测试记录，作为后续版本基线。

性能测试不建议默认全部加入高频 CI 阻断。推荐做法是：

| 类型 | 执行频率 | 是否阻断 |
|---|---|---|
| API 调用次数与日志调用次数 | 每次提交 | 阻断 |
| 单函数耗时基线 | 重要性能相关修改后 | 阻断或需解释 |
| 资产池扩展敏感性 | 扩展资产池前 | 阻断 |
| 本地微基准绝对秒数 | 手工记录 | 不直接阻断 |

| C3-PERF-003 | profile 开销对比 | 同区间跑 profile on/off 两组 | 关闭 profile 后耗时应不高于开启 profile；若差异明显，正式长测关闭 profile | A/B 耗时 |
| C3-PERF-004 | 日志量压力 | 默认参数，至少 1 年 | 日志可读且不刷屏，调仓日仅输出模块级中间量 | 日志样本 |
| C3-PERF-005 | API 取数稳定性 | 默认参数，至少 1 年 | 不因 API 频率、返回结构或字段调用过多中断 | 回测无异常 |
| C3-PERF-006 | 高窗口压力 | 测试参数提高 `RSRS_M` 或 `CrowdWindow` 后短测 | 耗时增加可解释，不影响默认参数结论 | 测试参数记录 |
| C3-PERF-007 | 资产池扩展压力 | 临时扩展到 5 至 8 只 ETF 短测 | 可运行且耗时增长可接受，若明显变慢需优化后再扩池 | 短测耗时 |
| C3-PERF-008 | 周频调度效率 | 长周期默认参数 | 调仓次数接近交易周数，不出现日频误触发 | 调仓日志日期 |

### 5.5 性能优化触发条件

| 触发条件 | 必须动作 |
|---|---|
| `get_price` 调用次数超过 4 | 优先检查是否引入逐 ETF 取数字段循环 |
| RSRS 或拥挤度耗时增加超过 50% | 检查是否引入 Python 层逐日循环或重复 rolling |
| 云端长周期耗时增加超过 30% | 做 profile on/off 对比，并抽查日志量 |
| 云端回测超时或卡住 | 先缩短区间定位，再按取数、RSRS、拥挤度、日志顺序排查 |
| 扩展资产池后耗时非线性上升 | 先优化批量计算，再决定是否保留扩展资产池 |
| 日志量明显过多 | 保留调仓日模块摘要，移除逐日调试日志 |
